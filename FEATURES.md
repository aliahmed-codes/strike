# Features

This file is the single source of truth for **what exists, what's in progress, and what's next**. Every piece of work — infrastructure or product feature — must have an entry here before it's started, and its status must be kept current.

Read this file together with [CLAUDE.md](./CLAUDE.md) (project context) and [DEV.md](./DEV.md) (how to work day-to-day).

## The rule: one step at a time

We do not build several things in parallel or in one long unattended stretch. For every feature in the backlog below, work happens in this exact order, and each stage gate must pass before the next one starts:

0. **Plan first.** Before writing any code for the step, state the approach (what will be built, which files/endpoints, what will be tested) and get a go-ahead. Don't skip straight to implementation just because the next item is obvious from the backlog. If there's more than one reasonable way to build a piece of it, ask which one instead of picking silently.
1. **Backend first.** Build the API for the feature (migrations, models, controllers/services, routes, validation).
2. **Backend tests.** Write test cases for every endpoint the feature adds (happy path + key failure paths). Run them. They must pass.
3. **Frontend.** Only after step 2 is green, build the UI for the feature against the real API.
4. **Test plan.** Write a short manual (or automated, where practical) test plan for the frontend flow, execute it, and confirm it passes.
5. **Explain it.** After finishing a step (or a meaningful chunk of one), give a complete, plain-language summary of what was actually built and how it works — enough for a non-implementer to fully understand what changed, not just "tests passed."
6. **The user tests it personally.** Automated tests passing is necessary but not sufficient. Wait for the user to try it themselves and confirm it's good.
7. **Commit.** Only once backend + tests + frontend + test plan all pass **and the user has personally confirmed it works**, create a git commit for that feature. **Do not start the next feature before this commit exists.**

If a stage fails, fix it and re-run that stage's tests — don't skip ahead.

## Users table: schema alignment with the old system

To avoid a painful data migration later, the `users` table was checked column-by-column against the old app's actual schema (`priceframe_schema.sql` / `1746000000001_create_identity_system.ts`) and deliberately adopted the fields that are cheap now and costly to add later:

**Adopted now:**
- `first_name` + `last_name` (split, matching the old schema) instead of a single `full_name` — splitting a name after the fact is lossy; done via a proper migration with a backfill, not a data-dropping rewrite.
- `is_active` (boolean, default true) — and it's actually **enforced**: login rejects a deactivated account with 403. A schema column with no behavior behind it isn't worth adding.
- `phone` (nullable) and `timezone` (default `UTC`) — harmless, commonly needed regardless of the old system.

**Deliberately NOT adopted** (would reintroduce complexity CLAUDE.md already says to defer until there's a real need):
- Normalized `roles` and `profiles` **tables** with hierarchy (`parent_role_id`) — we use a simple `role` enum instead (see CLAUDE.md's auth model). If/when item #5 (roles & permissions) needs more than 3 fixed roles, revisit this as its own decision.
- `manager_id`, `created_by`/`modified_by` audit columns, `deleted_at` soft-delete — no feature needs these yet.
- Account lockout fields (`failed_attempts`, `is_locked`, `locked_at`) and MFA fields (`mfa_enabled`, `mfa_secret`, etc.) — real security features, but nothing has asked for them yet; add the columns *when* that feature is actually built, not speculatively.
- Firebase/SSO fields (`firebase_uid`, `auth_provider`, `firebase_email`) — no SSO requirement exists for this rebuild.

If a future data-import task needs any of the "not adopted" fields, that's the point to add them — as their own scoped feature with its own migration, not retrofitted quietly.

## Quoting: full scope and phases (item #4)

This is the main feature the client sees — a "New Pricing Request" with 7 tabs: **Summary, Setup Fee, Pricing, P&L, Quoting Summary, Legal, Approvals**. Investigated the old app's real implementation of all 7 tabs before designing this (see git history for the research); the old system had real weaknesses we're deliberately not repeating:

- **All P&L/revenue/margin numbers were computed in the browser** and stored as an opaque JSON blob — no backend source of truth. **We do it properly: the backend computes and owns every number** (`app/services/quote_pricing_service.ts`); the frontend only displays them.
- **Setup Fee and P&L had no real database tables** — JSON blobs on the quote. We use real, normalized columns/tables instead.
- Duplicate near-identical columns (`standard_fixed_fee_usd` vs `std_fixed_fee_usd`, parallel `_precise` copies of every numeric field) — not repeated here; one canonical numeric column per value.

**Database note:** reference/corridor data is real, not invented. Regions, countries (207, incl. Syria which the old app's own catalog mistags as region "Africa" — kept for exact parity), currencies (97, covering every currency the real corridor catalog uses), use cases, integration types, ICP hierarchy, and pegged rates come from the old app's live database and its hardcoded UI option lists — exported as JSON under `database/data/real_*.json` so seeding doesn't depend on a live connection to that database. The corridor catalog (1,271 rows) is the old app's actual active production corridor version, deduped on the exact same key the old app's own picker uses (verified row-for-row: total count, region counts, and service counts all match the old app exactly).

### Phase 1 — Quote + Corridors + Pricing core — ✔ backend done, tested, committed

- `corridors` — the catalog a user picks from when adding a corridor to a quote.
- `quotes` — header: name, status (draft/submitted/approved/rejected/closed), owner, opportunity type, partner country, use case(s), integration type, 3 independent ICP levels, contract length, currencies, plus (added once real Summary-tab screenshots arrived) `show_fx_source_in_contract`/`show_fx_spread_in_contract`, `fx_model`, `selected_pricing_strategy`, `selected_fx_pricing`, `default_fee_currency_id`.

- `quote_corridors` — one row per corridor on a quote: inputs (volume, transactions, fixed fee, variable fee %, FX spread, discount %) and backend-computed outputs (revenue, FX margin, total revenue/margin, take rate, `needs_approval` + reasons).
- `app/services/quote_pricing_service.ts` — the single source of truth for all pricing math. **Formulas are a documented first pass** (see comments in that file), not yet confirmed against real finance/business rules — centralized in one file specifically so they're easy to audit/adjust without touching controllers, models, or the frontend.
- `app/services/corridor_facet_service.ts` + `GET /reference/corridors/facets` — per-dimension corridor counts (region/country/service/transaction-type/payout-currency/payer) given any combination of active filters, powering the "Corridors to Offer" picker. Matches the old app's exact (verified against its real code) narrowing rule: Region is a one-way top-level filter — it narrows every other panel but is never itself narrowed by anything; the other five panels form a fully mutual facet (each narrowed by every other active filter, never by its own). Every panel always lists every value that exists in the catalog — a 0-count value stays listed (for the UI to disable, not remove) rather than disappearing. Supports "Hide USD SWIFT" and a `restrictToUseCaseAllowedCountries` flag (the old app's compliance rule restricting the picker to a fixed country allow-list when the quote's use cases include "Last Mile Payout" or "Account Top-Up").
- Endpoints: `GET/POST /reference/*` (lookups + catalog + facets), `GET/POST/PATCH/DELETE /quotes`, `POST/PATCH/DELETE /quotes/:id/corridors/:id`. A quote is only editable (header or corridors) while `status = 'draft'`; an owner sees only their own quotes, an admin sees all.

- **Frontend: done, tested, committed.** A dynamic, closable tab workspace (`useQuoteWorkspaceStore.ts`, Zustand + `persist`) — "New Pricing Request" opens a client-only draft tab (no backend row until first Save, confirmed matching the old app's real behavior), reused if an empty one is already open, restored across refresh, and prompts with a styled confirm dialog before discarding unsaved changes on close. Setup Fee tab shows a placeholder until its backend exists (Phase 2).

### Phase 1b — Pricing tab parity closure — ▶ in progress

While building Phase 2 we re-compared the shipped Pricing tab against the old app's real one (a general-purpose agent read both in full) and found Phase 1's Pricing tab, while functionally correct for what it covers, is missing real business logic the old app has — not just styling. Reopening this rather than folding it into a later phase, since it's the same feature. Scope, in build order:

1. **Missing computed columns per corridor**: FX Margin, FX Margin %, Margin Fee, Gross Margin % — old app computes and displays these; new app currently only shows Revenue, Margin, Take Rate. Backend: extend `quote_pricing_service.ts` + add columns to `quote_corridors`.
2. **Approval-type distinction** — old app's `checkCorridorApproval` separates *financial* approval from *network* approval, each with its own trigger conditions and instruction text; new app only shows one generic "Needs Approval" flag with no distinction or guidance.
3. **Tiered/volume-based pricing** — this is backlog item #6 ("Corridor catalog & tiered/volume pricing"), previously deferred on purpose, now being pulled into this closure pass at the user's request for full parity. **Backend done, tested, not yet committed** — a thorough investigation (two research-agent passes) found the old app's tiered pricing was never actually finished: both options were commented out of its only selector, so it's dead code in production, and the implementation had real bugs (an inverted, unintuitive tier-discount direction — Tier 1 got the biggest discount, Tier 3 the smallest; per-tier fee/spread columns labelled as editable "setup" fields but actually locked read-only; a volume-vs-revenue comparison bug in the FX-spread fallback logic; no real per-tier approval enforcement at all, despite looking like there was). Given there was no working reference to port, this was rebuilt as a cleaned-up version of the old intent rather than a faithful port — decided with the user rather than guessed at:
   - Tier numbering fixed to the intuitive direction: Tier 1 = smallest discount, Tier 3 = biggest.
   - Per-corridor toggle (`quote_corridors.pricing_model`), not per-quote like the old app — a quote can mix standard and tiered corridors freely, since each corridor is already independently priced in this schema.
   - A corridor's volume splits across up to 3 tiers (each with **genuinely** editable Fixed Fee/Variable Fee %/FX Spread, unlike the old app), with whatever's left over pricing at the corridor's own existing standard fields — no separate "Tier 0" concept needed.
   - **No new pricing formula** — every tier (and the standard remainder) is just another call to the same `computeCorridorPricing` from item (1)/(2), summed together. Per-tier financial/network approval comes for free from this reuse.
   - Each tier's transaction count is derived from its volume ÷ the corridor's ATV (the one part of the old app's math that wasn't buggy), instead of asking the user to keep per-tier transaction counts in sync by hand.
   - New table `quote_corridor_tiers` (one real row per tier, computed outputs included) — deliberately not the old app's asymmetric model (a flat "Tier 0" plus an opaque, unvalidated JSON blob for everything else).
   - Validated at the boundary: tier volumes can never sum to more than the corridor's total.
   - 14 new tests (10 unit + 4 functional) — all passing, plus a live end-to-end check against a real corridor (correct math, correct reload-after-save).
   - **Frontend: done, not yet tested by the user.** Pricing tab gets a per-corridor "Pricing" dropdown (Standard/Tiered) and, when Tiered, an "Edit tiers" panel — up to 3 tiers, each with genuinely editable Fixed Fee/Variable Fee %/FX Spread, a live "Standard remainder" readout, and the same real-time preview pattern as everywhere else (the row's Revenue/Margin/Approval columns update live while editing tiers, using `computeTieredCorridorPricing` from `@strike/shared` — no drift from what the backend will actually save). Tier volumes are validated live against the corridor's total, blocking Save when over-allocated. Postman collection updated with an "Add Tiered Corridor to Quote" example. Test plan: `docs/test-plans/tiered-pricing-frontend.md`. One of the sample quotes ("Acme Corp") has a corridor already set to Tiered for a quick look.
3.5. **Field-parity pass** — comparing our shipped Pricing tab column-for-column against the old app's real one turned up several fields we'd genuinely missed (not just cosmetic): Margin % (we computed it already, never displayed it), the corridor's own cost/FX master data shown read-only for transparency, and — a real gap — the catalog's "Standard" reference fee (so a salesperson can see how far their quote deviates from it), which we'd never even imported. Also added: Fee Discount % as a visible/editable column on already-added corridors (previously only settable when first adding one), a fee-in-funding-currency conversion, and a Historical ATV reference. **Done, tested, not yet committed:**
   - Backend: imported 2 more real fields per corridor (Std Fixed Fee, Std Variable Fee) from the same source as the other master data (~1,260/1,271 matched); imported the old app's real `currency_rates` table (14 currencies, an XE mid-market average — not a live rate feed) onto `currencies.fee_conversion_rate_to_usd`; imported real Historical ATV from the old app's `corridor_atv` table onto `corridors.historical_atv` (~642/1,271 matched — keyed by service+country+transaction type only, same looser key the old app's own data uses, no payer). All three fields are nullable and null means "no data" — **never a fabricated fallback value** (the old app's own currency-rate cache silently falls back to a 1:1 rate for uncovered currencies; we deliberately do not copy that, since it's a real bug, not a feature).
   - Frontend: Std Fixed Fee/Std Variable Fee shown as read-only reference columns, Fee Discount % is now an editable column on every row (not just when adding), Margin % added as its own column. A per-row "Details" panel (separate from the tiers panel) shows the corridor's Treasury FX Cost Spread %/Fixed Cost/Variable Cost, Historical ATV (or "No data"), and the fixed fee converted into the deal's funding currency (or "No rate available"). Funding Currency and ATV (USD) are now also visible/editable columns on every row (previously only settable when first adding a corridor).
   - **A real bug found and fixed while doing this pass**: comparing our columns against a real screenshot of the old app showed "Margin Fee %" and "Margin %" as two distinct, adjacent columns — we only had one (`marginPct`), and it turned out to be computing the old app's "Margin Fee %" formula (margin fee ÷ volume, excluding FX margin), not its real "Margin %" (total margin, *including* FX margin, ÷ volume — a genuinely different number whenever FX margin is positive). Fixed at the source in `corridor_pricing_math.ts`/`tiered_pricing_math.ts`: `marginPct` now computes the correct (total-margin) formula, and a new `marginFeePct` field carries the fee-only one under its own honest name. Added a `margin_fee_pct` column to `quote_corridors` and both `margin_fee_pct`/`margin_pct` to `quote_corridor_tiers` (which never had a stored `margin_pct` at all before this). 1 new + 1 updated unit test lock in the distinction (equal when FX margin isn't positive, `marginPct > marginFeePct` when it is).

   - **FX Source as a user-editable per-corridor dropdown — still open, needs the client's input.** Checked the old app's actual database: `fx_source` is a real, saved, per-quote-corridor column (confirmed real values like "Reuters Bid Rates", "Like for Like" on real historical quotes), not just a display of catalog data — the old app also auto-recomputes it whenever the deal's Funding Currency changes (with "Like for Like" corridors specially exempted from that auto-recompute). The old app's "Source Currency" column is just the quote-level value repeated on every row for display, not a real per-corridor field. **Added**: a read-only "Source Currency" column showing `quote.sourceCurrency` on every row, matching the old app's actual (display-only) behavior — no schema change needed.

4. **Frontend-only, no new tables**: a Summary rollups panel (Total Corridors/Volume/Transactions/Revenue/Average Take Rate) above the corridors table; column filters (region, country, service, currency, approval status, negative-margin flags) and sorting; a "Download Corridors" Excel export (client-side, mirrors the old app's approach of exporting the currently-displayed table — no backend involved).

**Approved build order (2026-09-16), to be done one phase at a time with a plan/approval checkpoint before each:**

**Phase A — Explicit corridor saving (buffered edits) — ✔ built, not yet tested by the user.** Replaced save-on-blur/dropdown-change with the old app's real model: edits to a row (existing saved or still-preview) are staged locally (pricing keeps recalculating live, client-side, exactly as before) and only sent to the server when the new "Save Edited Corridors" button is clicked. No backend changes — per the decision above, save loops the existing `PATCH /quotes/:id/corridors/:id` (for already-saved rows) and `POST /quotes/:id/corridors` (to promote a dirty preview row) once per dirty row, sequentially, each independently — one row failing never blocks or discards the others.
- Staged edits now live in a new persisted Zustand store, `useCorridorEditsStore.ts` (keyed by `tabKey` → row key), instead of `PricingTab.tsx` component state — this is what makes them survive switching to the Summary tab and back, since Radix's `TabsContent` unmounts inactive tab panels by default (confirmed this was actually broken before this change).
- Fixes the old app's worst bug from this area (reference doc §1) rather than copying it: a row's staged edits are only cleared *after* its save call actually succeeds — never optimistically beforehand — so a failed save can never silently lose an edit. On failure, the failed row(s) stay staged and visibly marked unsaved, and a non-blocking inline error banner names them (not a blocking `alert()`).
- Row styling uses an intuitive convention, the opposite of the old app's confusing inverted one: a dirty saved row is blue-tinted with an "Unsaved changes" badge; a not-yet-saved preview row keeps its existing amber "Not saved" badge; a clean saved row is plain.
- A real bug caught while building this: reading a saved row's pending funding-currency edit with `??` would have treated an explicit "clear to —" (staged `null`) as "no pending edit" and silently fallen back to the old saved value — fixed by checking the key's presence with `in` instead of relying on nullish-coalescing.
- Test plan: `docs/test-plans/explicit-corridor-save.md`.
- **Follow-up UI cleanup (2026-09-16), at the user's request:** removed the standalone "Add a Corridor" form/section from the Pricing tab entirely — adding a corridor now only happens through the "Corridors to Offer" filter → preview row → edit → Save Edited Corridors path (see 5.5 above), which is now the one consistent way to add a corridor instead of two parallel paths. Also made "Corridors to Offer" start collapsed on the Pricing tab specifically (still open by default on the Summary tab, where it's the primary thing a user does first) — added a `defaultOpen` prop to `CorridorsToOfferSection`/`CollapsibleSection` for this.

**Phase B — Multiple funding currencies per corridor — backend and frontend done and tested (automated), pending the user's manual browser test.** A corridor matching the quote's filters should produce one row per funding currency selected on the quote, each independently priced and saved. Requires: one deterministic composite row key (e.g. `${corridorId}:${fundingCurrencyId}`, not the old app's conditional pipe-key/synthetic-id split — see reference doc §2), a real DB unique constraint on `(quote_id, corridor_id, funding_currency_id)` on `quote_corridors` (the old app never had this — its own normalized redesign for it, `v2.quote_corridors`, was designed but never wired up), and per-funding-currency FX rule branches ported cleanly (not the old app's scattered hardcoded EUR/XAF, EUR/XOF special cases — consolidate into one data-driven table if we need those same rules). **Decided with the user (2026-09-16): a row's funding currency becomes fixed/read-only** once it exists (saved or preview) — no more editable dropdown on a row. A row's currency comes from which of the quote's funding currencies it was generated for; to change it, remove the row and let it reappear as a preview under the intended currency. Simpler than making the dropdown itself conflict-aware (blocking a change that would collide with another already-existing row for the same corridor+currency).
- **Backend, done and tested:** the original `quote_corridors` table migration had `UNIQUE(quote_id, corridor_id)`, which would have blocked this feature outright (the same corridor could never be saved twice, under any funding currency). Migration `1789500000000` drops that and replaces it with a real composite unique index on `(quote_id, corridor_id, COALESCE(funding_currency_id, -1))` — the `COALESCE` matters because Postgres treats every `NULL` as distinct from every other `NULL`, so a plain multi-column unique constraint would let "no funding currency" rows collide silently past it. The corridor-add duplicate check in `quote_corridors_controller.ts` is now scoped the same way (by corridor **and** funding currency, not corridor alone). `fundingCurrencyId` was removed from `updateQuoteCorridorValidator` entirely, enforcing the "fixed once saved" decision above at the API boundary, not just in the frontend UI. 3 new tests (same corridor under two funding currencies succeeds; same corridor + same funding currency twice is rejected; a PATCH attempting to change `fundingCurrencyId` is silently ignored) — all passing, 108/108 backend tests green.
- One implementation pitfall worth remembering for future migrations in this codebase: Lucid's `this.schema` is a getter, and *accessing* it (not just calling a method on it) queues its return value to run later — accessing it twice in one migration (e.g. once for `alterTable`, once more for `.raw`) queues the same underlying builder twice, so it silently executes twice. Fixed by capturing `const schema = this.schema` once and chaining every call in that migration off the same reference.
- **Frontend, done, automated checks passing (build/typecheck/lint), pending the user's manual browser test:** `PricingTab.tsx`'s row-generation loop now produces one preview row per matching corridor **per funding currency on the quote** (falling back to a single currency-less row when the quote has none selected, unchanged from before). One canonical composite key (`preview-${corridorId}:${fundingCurrencyId ?? 'none'}`) identifies each preview slot — deliberately not the old app's two inconsistent schemes for the same concept (a pipe-delimited business-field key vs. a synthetic `${id}_${currency}` id, see reference doc §2). The "already saved" and "dismissed" tracking (which used to hide a preview once its corridor existed at all) are now scoped to the corridor+currency pair, so saving or dismissing one currency's row never affects another currency's row for the same corridor. Per the earlier decision, the Funding Currency column is now a fixed label (not a dropdown) on every row, saved or preview — to change it, remove the row and let it reappear as a preview under the intended currency. `fundingCurrencyId` was removed from the client's pending-edit type entirely, matching its removal from the backend's update validator. Test plan: `docs/test-plans/funding-currency-rows.md`.
- **Real bug found during the user's own manual test, fixed (2026-09-16):** promoting the second funding-currency's preview row failed with a 500 ("duplicate key value violates unique constraint quote_corridors_quote_id_corridor_id_unique"). Root cause: the Phase B migration had been run and verified against the *test* database, but never actually applied to the local *dev* database the running server and browser use (`node ace migration:status` confirmed it as `pending` there) — a deployment-step gap, not a logic bug. Fixed by running `node ace migration:run` against dev; re-verified the exact failing request now returns 201. Separately, the "Save Edited Corridors" button being disabled while corridors are only previewing (before anything is edited) is expected, not a bug — a preview row only becomes dirty/savable once one of its fields is actually edited, per the explicit-save design (Phase A).
- **Second real bug found on retest, fixed (2026-09-16):** the save kept failing with "Couldn't save 1 corridor" no matter what the user did, always the same count. Root cause: `dirtyRowKeys` counted every key ever staged in the persisted `useCorridorEditsStore`, including a stale one left over from before Phase B's row-key format existed (or a preview whose corridor+currency pair had since been saved through another path) — a key that no longer matched any currently-displayed row, so it could never be saved successfully, yet was retried on every click. Fixed by scoping both the displayed count and the actual save loop to keys that match a currently-displayed row (`displayRows`), so a stale/orphaned edit is simply never processed again instead of permanently blocking the button. **Third real bug found in the same pass:** the Pricing tab's row order visibly shuffled after every save. Root cause: `QuotesController#show` loaded `quote.corridors` with no `orderBy` at all — Postgres doesn't guarantee row order without one, so every refetch (which happens after every save) could return the same rows in a different order. Fixed with `orderBy('id', 'asc')` on that relation load. 108/108 backend tests still passing after both fixes.
- **Fourth real bug found on retest, fixed (2026-09-16):** changing "Corridors to Offer" filters sometimes blanked the whole panel down to a "Loading…" line (collapsing the page's height and shifting scroll position) before snapping back. Root cause: `useCorridorFacets`/`useMatchingCorridors` had no `placeholderData`, and every distinct filter combination is its own React Query cache key with no data yet — so `isLoading` flipped true on every filter change, not just the genuine first load, and the UI treated that the same as "nothing to show yet." Fixed by keeping the previous filter's data on screen (`placeholderData: (previous) => previous`) while the new request is in flight, with a small "— updating…" label next to the match count instead of blanking the panel. This doesn't reintroduce the earlier stale-matches bug (that was about *wrong* comma-parsed results, not merely showing last-known-good data for a moment) — real data always fully replaces the placeholder once it arrives.
- **Fifth real bug found on retest, fixed (2026-09-16):** narrowing the funding currency or transaction type selection kept showing the same, un-updated preview rows. Root cause: the Pricing tab read `quote.fundingCurrencies` — the last *saved* value — instead of the pending (unsaved) selection Summary's "Technical Pricing Details" actually shows, which like every other quote-header field is buffered locally until "Save Draft". Fixed by reading it through the same `useQuoteFormField` layering every other buffered field already uses.
- **Sixth real bug found on retest, fixed (2026-09-16):** refreshing the page while on the Pricing (or any non-Summary) tab always bounced back to Summary. Root cause: `QuoteEditorPage`'s `<Tabs>` was uncontrolled (`defaultValue="summary"`), so every fresh page load reset to it regardless of which sub-tab was actually open. Fixed by making it controlled, persisting the active sub-tab per quote tab in `useQuoteWorkspaceStore` (same persisted store already used for open tabs and pending fields).

**(1) and (2) — done, tested, and committed (backend + frontend).** A general-purpose research agent extracted the old app's exact, active formulas from its real code (`client/src/features/quotes/lib/pricing-calculations.ts` / `PricingTab.tsx` — its "server" does essentially none of this math; everything lived in the browser as JS floats). Key finding while implementing: the real formulas need per-corridor master data (FX Source, Treasury FX Cost, cost basis, and the Need Approval/Internal/Central Bank compliance flags) that Phase 1's original corridor export never captured — only routing/identity fields. Re-exported this data from the old app's live database (`corridors_list.corridor_details`, its currently-active catalog version) as `database/data/real_corridor_pricing_data.json` and wired it into `reference_data_seeder.ts` so it backfills automatically on every seed — 1,263 of our 1,271 corridors matched (8 don't exist in the old app's *current* active version due to catalog drift since Phase 1's original export; left null, never guessed).

`app/services/quote_pricing_service.ts` now computes:
- **FX Margin** using the corridor's real FX Source: `yearlyVolume × spread` for Cost-Plus corridors, `0` when funding currency equals payout currency (non-Cost-Plus), otherwise `yearlyVolume × (spread − treasuryFxCost)`.
- **Margin Fee** as `revenueFee − (corridor's real fixed + variable cost basis)` — previously this was a placeholder equal to revenue because no cost data existed at all.
- **Gross Margin %**, **FX Margin %**, **Take Rate** from the above, matching the old app's real definitions.
- **Financial approval** (`needs_financial_approval`/`financial_approval_reasons`): gross-margin floor by opportunity type (New Partner 60%, Upsell 45%, otherwise only flags on a *negative* margin — the old app's real `GM_THRESHOLDS`), fee discount over 35%, B2B transaction type (always flagged, matching the old app's real rule), Like-for-Like B2B variable fee floor, and a margin-percent-of-volume floor (0.25% B2B / 0.35% non-B2B).
- **Network approval** (`needs_network_approval`/`network_approval_reasons`): a pure lookup on the corridor's own Need Approval/Internal/Central Bank catalog fields (not a calculation) — clear only if all three are clean; a corridor with no catalog data at all is flagged for manual verification rather than silently assumed safe.

`needs_approval`/`approval_reasons` stay as the OR/concatenation of both, so nothing that already reads them breaks.

**Deliberately not replicated** (documented in the service file, not guessed at): the old app's Cost-Plus-with-partner-revenue-share FX branch (needs a Market-Based-Pricing "partner share" input we don't have), a EUR→XAF/XOF zero-spread special case (undocumented currency-pair quirk), and an "FX spread below minimum spread" approval check (the old app's own code never actually populates that minimum from real data either — a dead path in the source).

16 new/updated unit tests + all 65 backend tests passing. Postman collection updated.

**Frontend: done, tested, committed.** `computeCorridorPricing` moved into `packages/shared/src/lib/corridor_pricing_math.ts` (same pattern as Setup Fee's shared math module) so the Pricing tab can show a genuinely live preview using the exact function the backend uses to validate on save. Pricing tab now shows FX Margin %, Margin Fee, and Gross Margin % columns, and splits the old single "Needs Approval" flag into two independently-clickable badges (Financial / Network), each opening a popover with its own specific reasons. ### Phase 2 — Setup Fee — ✔ backend and frontend done, tested, committed

Investigated the old app's real implementation before building (it stored this entire tab as one unvalidated JSON blob — `pricing_tool_snapshot` on `quotes` — with zero server-side validation; every business rule lived only in React state). Rebuilt as 5 real normalized tables: `quote_setup_fees` (fee type, quoted price, payment schedule, MCF type/billing, waived months, rebate incentive, backend-computed `needs_approval`/`approval_reasons`), `quote_payment_milestones`, `quote_mcf_principal_slots`, `quote_mcf_block_fees` (Year-1 H1/H2 then per-year — the old app's true per-month grid was mostly vestigial in practice), and `quote_other_fees` (its real 12 fee-line-item concepts, not an unbounded blob array).

Deliberately fixes several real gaps found in the old app rather than copying them: full server-side validation (custom payment milestones must sum to exactly 100%, principal-based MCF requires the right slot count for the contract length, waived months capped at the old app's *actual* enforced max of 6 — its own input field misleadingly said 24); approval checks now cover all 12 "other fee" concepts instead of the old app's 5; one canonical revenue-threshold pair ($75k Year-1 / $150k total contract value) instead of two contradictory constants it carried. Upsell quotes bypass every setup-fee approval check, same as the old app's real (intentional) rule. `GET/PUT /quotes/:id/setup-fee`, same auth/ownership/draft-only pattern as every other quote-editing endpoint. 20-point test plan (`docs/test-plans/setup-fee-backend.md`) executed live against the running server, not just automated tests — all passing.

Also fixed while here: the backend test suite's per-test cleanup (`testUtils.db().truncate()`) started intermittently deadlocking/hanging once there were enough interlocking foreign keys — switched `tests/bootstrap.ts` to AdonisJS's transaction-rollback pattern (`withGlobalTransaction()`), which is both immune to that and ~4x faster. A global `pg` NUMERIC type-parser (`start/pg_types.ts`) fixes a real pre-existing bug found while testing this: `decimal` columns come back from a fresh Postgres SELECT as strings, not numbers — this affected the already-shipped corridors data too, not just this feature.

**Frontend**: `SetupFeeTab.tsx` — 5 sections (One-Off Fee, Monthly Commitment Fee, Other Fees, Rebate Incentive, Computed Summary), same "save the draft first" gate as the Pricing tab. The commitment-fee schedule math was pulled out into `packages/shared/src/lib/setup_fee_math.ts` so the frontend can show a genuinely **live** preview (Year 1/Total Contract Value cards that flip red/green as you type, matching the old app's real-time behavior) computed from the exact same function the backend uses to validate on save — no separate, potentially-drifting client-side copy of the formulas. Also live: Waived Months rejects/clamps anything over 6 immediately (not just on save), and the Custom payment schedule option disables itself below the $75k Quoting Price threshold and auto-reverts if the price drops below it while selected — both matching the old app's real-time behavior. Also removed a duplicate field found during this pass: `quotes.waived_months` (added during Phase 1, before Setup Fee existed) was a second, unvalidated source of truth for the same concept as `quote_setup_fees.waived_months` — dropped the column and the Summary tab's now-redundant field.
